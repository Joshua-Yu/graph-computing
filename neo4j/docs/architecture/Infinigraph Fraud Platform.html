01 · Premise

What actually decides this design

Three facts reshape the obvious architecture. None of them is throughput.

100 events/s is not the scaling problem

At a fan-out of roughly one event node plus four relationships, peak ingest is about 500 write operations per second — comfortably inside what a single Neo4j leader sustains. The rolling 30-day eviction adds about as much again. Plan for ~1,000 write ops/s steady state and stop worrying about the write path; spend the engineering on identity resolution, ordering and idempotency instead.

Infinigraph shards properties, not topology

This is the detail that changes sizing. The graph shard holds every node, relationship, label and id in a single Raft group — the topology is not partitioned and must fit one machine. Only properties hash-distribute across property shards. For this workload topology is ~200–250 GB (fits comfortably) and properties are ~650 GB–1 TB (the bulk). That ratio is exactly what property sharding is built for, which is why Infinigraph is a defensible call here rather than a premature one.

Deployment constraint

Sharded property databases require an Infinigraph subscription on Neo4j Enterprise and are not available on Aura. This tier is self-managed on EC2 or EKS — with the backup, patching and cluster operations that implies.

MERGE degrades on sharded property databases

Neo4j documents that MERGE performs poorly at scale on these databases, because its nested loop joins do not optimise across shards. Both of your write paths — daily customer/account upserts and idempotent event ingest — are MERGE-shaped by default. This is a hard design constraint on every Orchestra pipeline, not a tuning detail. Section 06 covers the pattern that replaces it.

Spread evenly that is roughly 100 node-deletes and 400 relationship-deletes per second running continuously alongside ingest. Budget for it, schedule it off the daily batch peak, and never let it accumulate into a weekly bulk delete.

03 · Topology

Overall shape

One decision organises the whole platform: the graph is not the system of record. Every event is tee'd at the broker into a hot path that maintains the 30-day graph and a cold path that lands immutable Parquet in S3. The graph becomes a disposable, rebuildable projection of the last 30 days — which is what makes aggressive eviction safe and what makes two-year history affordable.

04 · Ingest

Ingest and transport

Amazon MSK, sized for retention rather than throughput

At 100 events/s, throughput is irrelevant to broker sizing — three m7g.large brokers across three AZs are ample. Size the cluster for replay depth instead: seven days of retention is roughly 50–100 GB and buys you the ability to rebuild the hot graph from the broker alone after a bad deployment.

  • Partition by account_id. This preserves per-account ordering, which is what transaction semantics actually require, and it co-locates lock contention on hub nodes into a single consumer rather than scattering it across all of them.
  • Register schemas. AWS Glue Schema Registry with Avro or Protobuf. Event contracts between the fraud platform and core banking will change; an unversioned JSON blob turns every change into an outage.
  • Carry a deterministic event key. Idempotency has to come from the payload, because you are giving up MERGE.

Daily batch: customer and account deltas

AWS DMS in CDC mode, or Debezium on MSK Connect, onto the same broker. Routing batch deltas through Kafka rather than a separate file drop means one ingestion plane, one schema registry and one replay mechanism. Orchestra consumes the CDC topics on a schedule instead of continuously.

Schedule this off-peak

Daily deltas on customer and account touch high-degree nodes and will contend with event ingest for locks. Run the batch window when transaction volume is lowest, and pause the eviction job while it runs.

05 · Graph tier

The graph tier

Infinigraph splits a database into one graph shard carrying pure topology and N property shards carrying the property data, hash-distributed by id. Queries address a single logical database; the split is invisible to Cypher.

Choosing the number of property shards

Neo4j publishes no guidance on this. The syntax — SET PROPERTY SHARDS { COUNT n TOPOLOGY m REPLICAS } — accepts anything from 1 to 1000 and leaves the choice to you, so it is worth deriving rather than guessing.

Start by separating three numbers that are routinely conflated:

Three dials, one of which is expensive
DialSolvesCost to change
Shard count (COUNT n)How finely properties divide — and therefore how many servers you can ever spread them across Migration a full neo4j-admin database copy into a new database — offline, or online from a backup, then cut over
Replica count per shardRead throughput and redundancy. The default is 1, meaning no redundancy at all. Online no downtime
Server countAggregate page cache and CPU Online add servers, redistribute shards
The reframe that makes the number obvious

Raising n does not by itself add memory — aggregate page cache is servers × RAM, whatever the shard count. What n actually sets is the maximum number of servers you can ever spread properties across, since one shard per server is the finest granularity available. So n is not a sizing decision for today. It is a ceiling on future horizontal scale-out, chosen once, and the only one of the three dials you cannot adjust without downtime.

That makes the calculation a projection rather than a measurement:

Provision COUNT 8 at replica factor 2, and run it on the six servers a three-shard design would have used. Identical hardware today, three years of spread available without a copy-and-cutover, and eight divides evenly when you later move to 2, 4 or 8 servers. The three-shard figure is tighter than it looks: 656 GB across three shards is 219 GB each against ~85 GB of cache, which only holds while the hot fraction stays under about 40%.

The counter-pressure, and two costs of overshooting

More shards is not monotonically better. A query materialising properties for K entities contacts min(K, n) shards, so once K exceeds n every request touches all of them — and p99 becomes the p99 of the slowest of n responses. Sampling the tail n times per request is invisible at 4 and is not at 40, on a sub-100 ms budget.

Verify before choosing a large n

Whether property fetches dispatch to shards in parallel or serially is not addressed in public documentation, and it decides whether fan-out latency is the maximum across shards or the sum of them. At n = 8 the distinction is tolerable either way; past that it governs the ceiling. Ask Neo4j directly.

  • Backup cost scales linearly with n. Each shard carries its own chain, and property shard chains permit only one full backup with no differentials. Eight shards means eight full backups and an eight-way restore — the reason to overshoot moderately rather than maximally.
  • Hashing does not protect against co-location skew. Entities spread evenly by count, but a node’s outgoing relationship properties travel with it. Anchoring (:Account)-[:SENT]->(:Txn) as section 06 recommends means a settlement or corporate account with a million outgoing transactions concentrates a million edge-property records on one shard. Most accounts are tiny and average out; a handful will not. Identify the super-hubs before you model, and consider anchoring those specific entities the other way and accepting the scatter.
06 · Data model

Modelling for the shard boundary

There is no setting that keeps a property next to the topology. The graph shard holds none at all — so the question becomes how much of your filtering can be expressed as structure.

The execution model is specific and worth internalising: traversal runs entirely on the graph shard, and property lookups are batched and fetched at the final stage. That is the shape every query should have — structural predicates narrow the candidate set locally, then one batched fetch materialises what survives. A predicate on a property mid-pattern breaks it, because the planner must materialise a neighbour before it can test it.

The co-location rule worth designing around

Neo4j documents that a node’s properties and its outgoing relationships are assigned to the same shard. Direction therefore has a performance meaning it never had before. Model (:Account)-[:SENT {amount, ts}]->(:Txn) and one account’s entire outgoing edge-property set resolves from a single shard in one batched fetch. Model the same facts as (:Txn)-[:FROM {amount, ts}]->(:Account) and that read scatters across every shard. Anchor relationships outgoing from the entity your traversals start at.

Seeding a traversal by account number

A boundary on everything above

The promotion advice applies to low-cardinality filter predicates, not to high-cardinality identity lookups. An account number is the second kind. Structure never beats an index for exact lookup of a unique string — a prefix-bucket node with 100,000 children means scanning 100,000 relationships to find one, which is strictly worse than an index seek. Do not promote an identifier.

So the account number stays an indexed property. What matters is that it is the only property touched before the projection stage. One indexed seed, amortised across an entire query, is affordable even if it costs a shard hop; ten of them, or a property predicate mid-pattern, is not.

CREATE INDEX account_number_idx FOR (a:Account) ON (a.account_number);

A plain range index rather than IS UNIQUE or IS NODE KEY. A uniqueness constraint is validated on every write to :Account, and that check reaches a property shard — the same cost that makes MERGE slow in section 07. Identity is already resolved upstream in Orchestra, so the database does not need to re-prove it. Enforce uniqueness where you own it and let the index be purely a read structure. Keep one canonical key: every additional indexed property is more index memory and, if constrained, another cross-shard write check.

Then shape the query so the seed is the only property access until the end:

MATCH (a:Account {account_number: $acct})            // one indexed seed
MATCH (a)-[:WIRE_OUT]->(t:Txn)-[:TO]->(c:Account)   // pure topology
WHERE c:HighRisk                                     // label — graph-shard local
WITH a, t, c LIMIT 200
RETURN a.name, t.amount, c.name                      // one batched fetch

Seed, traverse structurally, project once. That shape holds whether or not the index turns out to be graph-shard local, which is what makes it the safe thing to build against while the question is open.

Exact lookup and search are different systems

Exact account-number lookup belongs in the Neo4j index above. Partial, prefix or typo-tolerant matching belongs in OpenSearch, which section 12 already provisions: resolve the string to an exact key there, then seed Neo4j with the key. Do not reach for a Neo4j full-text index for this — it is eventually consistent, heavier than a range index, and one of its refresh procedures is unsupported on sharded property databases in some versions.

You can settle the index question yourself

Once a cluster exists, PROFILE that query and read the plan for a cross-shard round trip on the NodeIndexSeek. That answers index residency empirically without waiting on Neo4j, and it is worth doing in the first week because it constrains the whole model. If the seed does prove to be a remote hop and it is hurting the real-time path, the contingency is a resolver cache in front — account_number → elementId, seeding later queries by element ID. One caveat makes it a contingency rather than part of the design: element IDs are not stable across a store copy, so a reshard becomes a cache-flush event.

What still costs you

  • Mid-pattern property predicates. Push them after the structural match — MATCH on topology, WITH the narrowed set, then WHERE on properties. Same results, one batched fetch instead of many.
  • Variable-length paths filtered on relationship properties. Documented as degrading; use quantified relationships (-[]->+) rather than -[*1..]->.
  • Uniqueness constraints on properties. The check has to reach a property shard on every write, which plausibly accounts for part of the MERGE penalty in section 07. Another reason to resolve identity upstream in Orchestra.
Unresolved — ask before you model around it

The public documentation does not say whether property indexes live on the graph shard or the property shards. That decides whether an indexed seed lookup such as MATCH (a:Account {id: $id}) is graph-shard local or already a cross-shard hop — and therefore how every traversal in the system should be keyed. Settle it with Neo4j before finalising the model.

07 · Write path

Writing without MERGE

Because MERGE is documented as slow on sharded property databases, identity resolution has to move upstream into Orchestra. The pattern is: resolve the business key to a known node key before the write, then issue a pure MATCH/CREATE over a large UNWINDed batch.

  • Deterministic keys. Derive node keys from the source system's identifiers so Orchestra can decide create-vs-update without asking the graph.
  • Node key constraints, then MATCH. An indexed unique lookup is cheap; MERGE's join planning is what costs you.
  • Large batches. Neo4j notes that batch-size gains are more pronounced on sharded databases than on single instances. Tune upward from 10k rows per transaction and measure — the reflex to keep batches small is wrong here.
  • Avoid variable-length syntax. Use quantified relationships (-[]->+) rather than -[*1..]->, which the docs flag as degrading when relationship properties are filtered across shards.
Also on the constraint list

Cypher 5 is unsupported — Cypher 25 only. Property-based access control for MATCH/TRAVERSE is unavailable, which matters if you planned to enforce data-segregation rules at the property level. neo4j-admin database copy cannot shard a database in place; you migrate to a new name or location.

08 · Retention

The 30-day window

Eviction is the most under-designed part of most graph platforms and, at these volumes, the larger half of the write budget. Three approaches are viable; only one survives contact with Infinigraph and GDS together.

Eviction strategies compared
ApproachMechanismVerdict
Time-partitioned databases One database per week, composite database over them, DROP the expired one — instant reclaim, no fragmentation. Rejected GDS cannot project cleanly across composite databases, and layering composites over sharded property databases compounds two young features. The cheapest eviction buys the most expensive analytics.
Rolling in-place delete CALL { … } IN TRANSACTIONS against a day-stamped index, run continuously as a background Orchestra pipeline. Recommended Costs ~500 write ops/s, which the cluster has spare. Keeps one database, so GDS and Infinigraph both behave normally.
Aggregate-and-drop Collapse raw events older than ~7 days into weighted TRANSACTED_WITH edges; delete the event nodes. Recommended alongside Cuts the resident event population by most of its volume while preserving the structure GDS actually needs for community and risk propagation.

What the window actually requires

“Thirty days online” is a sentence in a requirements document and a standing obligation in production. These are the requirements it implies, each of which has to be built rather than assumed.

Requirements implied by a 30-day rolling window
RequirementWhat it meansIf you skip it
Define the boundary Is the window measured on event time or ingestion time? Fraud telemetry arrives late by nature — chargebacks, disputes and confirmed-fraud labels land days to weeks after the transaction they describe. A chargeback for a 40-day-old transaction arrives to find its subject already evicted, and silently attaches to nothing.
Late-arrival policy An explicit rule for events whose subject is outside the window: rehydrate the subject from Iceberg, attach to the aggregated edge, or route to a review queue. Silent data loss in exactly the records an investigator is most likely to need.
Legal hold Entities under active case review are exempt from eviction until the case closes. The eviction job needs a hold mechanism and the case system needs to set it. Evidence disappears mid-investigation. This is a compliance incident, not a performance bug — and the hardest one to explain after the fact.
Continuous, resumable eviction ~100 node-deletes and ~400 relationship-deletes per second, checkpointed, able to fall behind and catch up without a burst. A weekly bulk delete creates a transaction spike that competes with ingest and can exceed the window it was meant to enforce.
Reclamation plan Neo4j reuses freed records, so the store reaches a high-water mark rather than growing without bound — but it does not return space to the OS. Compaction means an offline copy, which on a sharded database is a multi-shard operation. You provision for the average and are surprised by the high-water mark, with no affordable way to compact.
Window isolation Eviction must not overlap the daily batch window or a GDS projection run. Lock contention on exactly the high-degree nodes all three jobs touch.
Reconciliation A nightly count check between the graph and the Iceberg tables, proving the window is the width you think it is and nothing was orphaned. Drift accumulates invisibly until someone audits it.
Settle what “online” means before sizing anything

There is a large difference between 30 days of raw event nodes resident with full properties and 30 days answerable without the investigator waiting. The second is satisfied by aggregated relationships plus on-demand rehydration at a fraction of the resident cost. Which one you have committed to is a business question, and it is worth asking whether the 30 days is a regulatory obligation, an investigator expectation, or an inherited assumption — the three have different answers and only the first is fixed.

Run the second and third together: raw event nodes live ~7 days for investigator drill-down, aggregated relationships carry the remaining 23 days of signal, and the full-fidelity record sits in Iceberg for two years. That trims the resident graph substantially against the table in section 02 and leaves headroom for base-entity growth.

09 · Analytics

GDS placement and the write-back hop

GDS operates on the graph shard; property shards are transparent to it and managed automatically. It runs on a secondary with the plugin installed — which introduces a wiring problem that is easy to miss until integration testing: that secondary is read-only, so algorithm results cannot be written where they were computed.

Keep algorithms out of the request path

Real-time scoring at 100 events/s cannot wait on a community detection run. Split it:

  • Offline, scheduled (hourly or nightly): connected components, Louvain communities, PageRank, risk propagation — written back as node properties by the loop above.
  • Online, per event (<100 ms p99): a bounded 2–3 hop Cypher traversal with an explicit LIMIT, joined against those precomputed properties. Deterministic cost, no projection, no surprise.

Project subgraphs rather than the whole database. A projection of accounts plus aggregated transfer edges over the active window is roughly an order of magnitude smaller than a full projection, and it is what the fraud algorithms actually operate on.

10 · Application

Hume and Orchestra

Hume covers both the investigator frontend and, through Orchestra, the ingestion plane — which answers the question of whether to hand-roll Kubernetes Jobs for loading: you would be rebuilding Orchestra badly. Orchestra is the job runner, with native Kafka consumption, scheduling, retries and monitoring already built.

  • Deploy on EKS via GraphAware's Helm charts, in the same cluster and VPC as the graph tier. Orchestra workers scale horizontally; the front end and workers scale independently.
  • RDS PostgreSQL, Multi-AZ, for Hume's own connection and configuration state. This is operational metadata, not graph data — size it small and back it up conventionally.
  • Separate Orchestra instances by workload. Recent Hume versions let different knowledge graphs point at different Orchestra instances. Use that to isolate the continuous event stream from the daily batch and the eviction job, so a stuck batch cannot stall real-time ingestion.
  • ALB with OIDC in front of Hume, wired to your existing IdP. Investigator access to a financial-crime graph needs real SSO and audit, not local accounts.
  • OpenSearch Service if you use Hume's replication for free-text entity search — much better suited to name matching than a Neo4j full-text index at this scale.
11 · Archive

The two-year tier

"Queryable from sources" is satisfied by a lakehouse, not by the graph. Events land from MSK Connect into S3 as Iceberg tables registered in the Glue Data Catalog, partitioned by event date, and are queried with Athena. Lifecycle to Glacier Instant Retrieval at 90 days and expire at two years plus your retention margin.

The piece worth building deliberately is rehydration. When an investigation needs evidence older than the hot window, an Orchestra pipeline takes the case's entity set, runs an Athena query bounded to those entities and a date range, and materialises the result as a scoped investigation subgraph — a separate database, or a labelled partition with a TTL. This keeps two-year access a per-case cost rather than a permanent one, and it is dramatically cheaper than sizing the online graph for 24 months of events.

Sizing the archive

8.64M events/day × 730 days at ~600 B compressed is roughly 3–4 TB in Parquet — a rounding error in S3 terms, and a fraction of what the same history would cost held in Neo4j page cache.

Backup is not one artefact

A sharded property database is backed up shard by shard, producing multiple backup chains that must be kept consistent with each other. Each property shard's chain may contain only one full backup and no differentials, while the graph shard takes full plus differentials. Model your RPO and restore-time objectives against that asymmetry before you commit — it is materially different from backing up a single Neo4j database.

13 · Go / no-go

The Infinigraph decision

Infinigraph solves one problem: property volume beyond what a single instance can economically cache, while topology still fits one machine. Every other reason to adopt it is a bad reason.

Gate 0 — is the retention requirement itself fixed?

Take this gate first, because it is the cheapest thing in the system to change and it moves resident volume more than any tuning will. The 30-day window is the only major requirement here that is continuously adjustable, and the three plausible readings of it differ by ~220 GB.

The three readings, in full
OptionTopologyPropertiesTotalTrade
A — 30 d raw events206 GB656 GB862 GB Every event node resident with full properties for the whole window. Maximum investigator freedom, maximum cost.
B — 7 d raw + 23 d aggregated177 GB509 GB686 GB Recommended Raw drill-down where investigators actually work; aggregated structure preserves what GDS needs beyond it.
C — 30 d aggregated only169 GB470 GB639 GB Cheapest resident footprint, but every raw drill-down becomes a rehydration with a latency the investigator feels.
The counterintuitive part

Events are only 30% of property volume. The base entity graph — customers, accounts, devices — carries ~460 GB of the 656 GB, and it is not on a retention clock at all. If the goal is to defer Infinigraph, attack base entity property width, not the event window. Moving KYC documents, address history, free-text notes and any embedding vectors off customer and account nodes into S3 or OpenSearch is worth several times what shortening the window achieves.

Gates 1–4 — the architectural tests

Fail any one and the answer is defer, not proceed carefully
GateThresholdWhere you stand
Topology fits one machine, with three years of headroom Node + relationship + index stores measured on disk, against the largest instance you will buy. The graph shard is replicated, not partitioned — if this fails, Infinigraph does nothing for you. Pass 206 GB against 768 GB, 3.7× headroom
Properties are genuinely the bulk Property + string + array stores versus topology. Below ~2:1 you are buying distributed-systems complexity for nothing. Pass 3.2:1
A single instance is genuinely exhausted Hot working set — not total store — against ~1–1.5 TB. x2iedn.16xlarge holds 1 TB, .32xlarge holds 2 TB. Below that, buying RAM beats sharding on cost, complexity and risk. Fail 862 GB fits one instance today

Business blockers

These are binary. Any one of them is a stop regardless of how the volume curve looks.

  • Property-level access control. PBAC for MATCH and TRAVERSE is unavailable. For financial crime data this is live risk — segregating investigator access by jurisdiction, business line or case is a common obligation, and this pushes enforcement into the application layer where auditors are markedly less comfortable.
  • A managed-services mandate. Self-managed only today, with Aura stated as coming. If policy forbids self-managed stateful infrastructure, this is a wait, not a decision.
  • Data residency. Properties distribute by hash across cluster members. Whether placement can be constrained to a region is not addressed in public documentation — and hash distribution and residency pinning are fundamentally in tension. Resolve this first if it applies to you.
  • Contractual RPO. Backup is per-shard, and property shard chains permit only one full backup with no differentials. Validate your committed recovery point is achievable before signing, not after.
  • A regulatory delivery date. Putting an architecture your team has never operated on the critical path of a compliance deadline is schedule risk independent of whether the technology is sound.
  • Licensing economics. Infinigraph subscription plus GDS Enterprise plus nine instances, against Enterprise plus one or two large ones. There is a crossover point and it sits further out than the scale conversation tends to imply.

Exhaust these first

If any one of these brings you under the ceiling, Infinigraph is premature:

  1. Move cold properties out entirely — free text, vectors, document payloads and audit fields to S3 or OpenSearch, keyed by node id. Often 60–80% of property volume, and by a wide margin the highest-return move available.
  2. Shorten the raw window or aggregate sooner — Option B above.
  3. Split weakly-connected subdomains into separate databases with application-level joins.
  4. Buy RAM. Boring, and usually correct below a terabyte.
The trigger, stated as a measurement

Shape is right; timing is not. Re-evaluate when hot working set exceeds ~70% of the largest instance you are willing to buy, with twelve months of growth still ahead of it — and only after cold properties have been moved to object storage. Resolve PBAC and data residency now regardless, because those two can invalidate the direction whatever the volume curve does.

14 · Sequence

Phasing

Do not start on Infinigraph. It solves a property-volume problem and adds a young feature set and a separate subscription. Shard count is not a one-way door — replicas adjust online and shard count changes via a copy into a new database — but the data model is much harder to walk back. Earn your way in, and get the modelling right early.

  1. P1

    Single-instance baseline

    Standard Neo4j Enterprise cluster on an x2iedn-class instance. At ~860 GB total store, the whole graph plausibly fits one machine's page cache. Load real data, measure actual property width and store sizes, and establish the eviction pipeline.

  2. P2

    Split the workloads

    Add secondaries for scoring reads and a dedicated GDS analytics member. Build the feature write-back loop and the precomputed-property scoring path. This is where most of the latency engineering happens, and none of it depends on sharding.

  3. P3

    Archive and rehydration

    Stand up the Iceberg tier and the rehydration pipeline. Once this exists, the hot window is a tunable number rather than a data-retention commitment — which de-risks everything after it.

  4. P4

    Adopt Infinigraph when properties, not topology, are the constraint

    The trigger is measured: total store outgrowing what a single instance caches economically, while topology still fits one host. Migrate with neo4j-admin database copy to a new location — in-place conversion is not supported — and land the topology promotions in section 06 first, because they are far more disruptive to change afterwards than shard count is.

15 · Diligence

Open questions for Neo4j and GraphAware

Each of these could change the architecture. Get answers before the Phase 4 commitment, and ideally before contract.

  • Point-in-time recovery across shardsGiven the single-full-backup constraint on property shard chains, what is the achievable RPO and the realistic restore time for a ~860 GB sharded database?
  • Infinigraph on AuraNeo4j has stated it is coming to AuraDB. What is the timeline and the feature parity? If it lands within your build window, Phase 4 changes from a self-managed cluster to a managed one.
  • Hume and Orchestra certificationAre Hume's visualisation and Orchestra's loaders tested against sharded property databases on Cypher 25 — specifically the Orchestra loaders that generate MERGE by default?
  • Property fetch dispatchAre batched property lookups dispatched to shards in parallel or serially? This sets whether fan-out latency is the maximum across shards or the sum, and therefore the practical ceiling on shard count for the real-time scoring path.
  • Index residencyDo property indexes live on the graph shard or the property shards? This decides whether an indexed seed lookup such as MATCH (a:Account {id: $id}) is graph-shard local or already a cross-shard hop — and therefore how you key every traversal.
  • Constraint enforcement costHow is a uniqueness constraint on a property validated at write time across shards? This likely accounts for part of the MERGE penalty and determines whether node key constraints are affordable at 1.26B nodes.
  • Resharding in practiceResharding by copy into a new database is documented, including online from a backup; how long does copying a ~860 GB sharded database actually take, and can it be staged against a backup to avoid a maintenance window on the live cluster?
  • GDS write-backIs there a supported path better than stream-out-and-reload, and what property-shard load do large projections actually generate?
  • LicensingInfinigraph subscription, GDS Enterprise and Hume are three commercial licences on top of AWS spend. Model the total before the architecture is locked.
16 · Decision summary

Infinigraph or not

A self-contained summary of the adoption decision, written to be lifted into a solution architecture document. Each point refers back to the section that supports it.

Recommendation

Not yet: design for Infinigraph now, and adopt it at Phase 4 when the measured trigger is met. The workload has the right shape for property sharding: topology fits one machine, and properties outweigh it 3.2:1. But at ~860 GB a single large instance still holds the whole store in page cache. Build on standard Neo4j Enterprise, apply the shard-safe modelling and write patterns from day one so a later migration is a data copy rather than a redesign, and resolve the two business blockers (property-based access control and data residency) before committing.

Pros

What Infinigraph gives this platform
BenefitWhy it matters here
Property volume scales horizontally Properties hash across N shards on separate servers, so total page cache grows with server count. That matches a workload where properties (~656 GB) dominate topology (~206 GB). §05
One logical database, transparent to Cypher No application-level sharding, routing or federation. Queries address the database by its virtual name, and the split is invisible to Hume and the scoring service.
ACID preserved Transactions are coordinated on the graph shard's Raft group, and internal bookmarks give read-your-own-writes across shards. No consistency model to redesign around.
Traversal cache protected from bulky values Free text, device fingerprints and vectors leave the graph shard's page cache, so topology stays memory-resident. Neo4j positions the feature as suited to vector and full-text workloads.
Large headroom Vendor-stated capacity is up to 100 TB, far beyond any projection for this workload.
Online elasticity for two of the three dials Replica count and server count change without downtime. Over-provisioning the shard count and co-locating shards (vendor-recommended) buys future spread at no hardware cost today. §05
Stays inside the existing product family GDS runs on a graph shard secondary, and Hume connects over Bolt as usual. No second database technology to introduce.

Cons

Limits, costs and risks
LimitationConsequence
Topology is not partitioned Nodes, relationships, labels, IDs and indexes must fit one machine. If topology outgrows the largest host, Infinigraph does not help.
Writes go through a single leader Write throughput is that of one graph shard leader. Adequate at ~1,000 ops/s, but not a write-scaling solution.
Still shared-nothing; compute is not separate from storage There is no stateless query tier. Read scale-out means adding graph shard secondaries, each holding a full topology replica (~206 GB here), so read capacity costs storage-node hardware.
Query-pattern penalties MERGE is very slow at scale. Property filters on variable-length paths and shortest paths are not fully optimised. Cross-shard fan-out adds tail latency. §07
No property-based access control PBAC is unsupported, so attribute-level data segregation moves into the application layer.
Cypher 25 only Cypher 5 is not officially supported. Existing queries and tooling must be ported and tested.
Self-managed only, separate subscription Not available on Aura. Requires an Infinigraph subscription on Enterprise, on top of GDS and Hume licences.
Weaker HA on property shards Property shard replicas are not Raft members, so redundancy comes from replica count alone (M = F + 1).
Fragmented backup and restore Backups run shard by shard, and each property shard chain allows one full backup with no differentials. Restore is an N-way coordinated operation. §12
Shard count is fixed at creation Changing it means copying into a new database and cutting over. The copy can run from a backup while the live database serves, but it is still a migration.
Maturity Announced September 2025, with a feature set still changing release to release. There is little public operating experience at this scale.
